# 工具搜索

当一个会话附加了许多 MCP 服务器或非核心插件工具时，即使其中只有少数工具与用户实际提出的问题相关，它们的 JSON 模式也可能在每一轮占用上下文窗口相当大的一部分。

**工具搜索** 是 Hermes 针对该问题的选择加入式渐进披露层。激活后，MCP 和插件工具会在模型可见的工具数组中由三个桥接工具替代，模型则按需加载每个具体工具的模式。

:::info 内置 Hermes 工具永不延迟加载
构成 Hermes 核心能力集的工具（`terminal`、`read_file`、`write_file`、`patch`、`search_files`、`todo`、`memory`、`browser_*`、`web_search`、`web_extract`、`clarify`、`execute_code`、`delegate_task`、`session_search`，以及 `_HERMES_CORE_TOOLS` 中的其余工具）*始终*直接加载。只有 MCP 工具和非核心插件工具可被延迟加载。
:::

## 工作方式

当工具搜索为某一轮激活时，模型会看到三个新工具来替代被延迟加载的工具：

```
tool_search(query, limit?)     — 搜索延迟加载工具目录
tool_describe(name)            — 加载一个工具的完整模式
tool_call(name, arguments)     — 调用一个延迟加载的工具
```

典型交互如下：

```
Model: tool_search("创建一个 GitHub issue")
  → { matches: [{ name: "mcp_github_create_issue", ... }, ...] }
Model: tool_describe("mcp_github_create_issue")
  → { parameters: { type: "object", properties: { ... } } }
Model: tool_call("mcp_github_create_issue", { title: "...", body: "..." })
  → { ok: true, issue_number: 42 }
```

当模型调用 `tool_call` 时，Hermes 会**解包桥接层**，并完全如同模型直接调用底层工具一样分派该工具。工具调用前钩子、护栏、审批提示和工具调用后钩子都会针对真实工具名称运行，而不是针对 `tool_call`。CLI 和网关中的活动信息流也会解包，因此你看到的是底层工具，而不是桥接层。

## 何时激活？

工具搜索使用**分层披露**：只要存在任一可延迟加载的（MCP/插件）工具，桥接层就会激活；随目录大小变化的是目录中有多少保持可见，而不是模式是否延迟加载。

| 层级 | 条件 | 模型看到的内容 |
| --- | --- | --- |
| **0** | 没有 MCP/插件工具 | 每个工具都急切加载，没有桥接层。直接透传。 |
| **1** | 延迟目录的列表可容纳在预算内 | 桥接层 + 每个延迟工具的技能风格清单（名称 + 简短描述；超出预算时降级为仅名称）。降级按**每台服务器**进行：当一个超大的服务器（Cloudflare）与小型服务器（Linear）同时附加时，小型服务器保留其逐工具列表，只有超大服务器折叠为摘要行。 |
| **2** | 即使每台服务器都仅列工具名称，逐工具列表仍超出预算（例如，仅 Cloudflare 的扁平 API 表面就有约 3,300 个工具，其名称约为 32K tokens） | 仅桥接层 + 每台服务器一行的摘要（服务器名称 + 工具数），让模型知道可访问哪些领域；各个工具只能通过 `tool_search` 发现。 |

列表预算为 `min(threshold_pct% of context, listing_max_tokens)`。每次构建工具数组时都会重新评估该决定，因此在会话中添加或移除 MCP 服务器会在下一次组装时使会话在各层级之间切换。

## 配置

```yaml
tools:
  tool_search:
    enabled: auto       # auto（默认）、on 或 off
    threshold_pct: 5    # 列表预算占上下文的百分比
    search_default_limit: 5
    max_search_limit: 20
    listing: auto       # 嵌入按组显示的名称+描述目录清单
    listing_max_tokens: 20000
```

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `enabled` | `auto` | 只要至少存在一个可延迟加载的工具，`auto`/`on` 就会激活；`off` 会完全禁用（所有工具保持急切加载）。 |
| `threshold_pct` | `5` | 列表预算占活动模型上下文长度的百分比。范围为 0–100。 |
| `search_default_limit` | `5` | 当模型调用 `tool_search` 而不提供 `limit` 时返回的命中数。 |
| `max_search_limit` | `20` | 模型可通过 `limit` 请求的硬上限。范围为 1–50。 |
| `listing` | `auto` | 在 `tool_search` 桥接工具描述中嵌入每个延迟工具的技能风格清单（名称 + 描述的第一句话，≤60 个字符，按 MCP 服务器分组）。`auto` 会在清单符合预算时包含它（依次回退到仅名称、再到第 2 层服务器摘要）；`on`/`off` 会强制启用或关闭。 |
| `listing_max_tokens` | `20000` | 嵌入式列表的绝对上限，与上下文大小无关。范围为 200–60000。 |

### 列表为何存在

没有它，延迟的能力就是**不可见的**——实际基准测试显示，模型会替代性地使用可见的核心工具（例如在终端中运行 `gh`，而不是搜索延迟加载的 GitHub 工具），或不调用 `tool_search` 就宣称某种能力不存在。该列表将技能模式应用于工具：每项能力始终可按名称发现，而完整的参数模式仍保持延迟加载。如果模型在列表中看到了确切的工具名称，它就可以跳过 `tool_search` 并直接进入 `tool_describe`，从而节省一次往返。

你也可以切换为旧版布尔值形式：

```yaml
tools:
  tool_search: true   # 等价于 {enabled: auto}
```

## 何时不应使用它

工具搜索以固定的每轮 token 成本（三个桥接工具模式加上目录列表）以及对冷工具至少一次额外往返（describe → call），来换取延迟模式的节省。在第 1 层，列表会保持每项能力可见，因此发现所需的往返通常会消失——模型会直接进入 `tool_describe`。实际基准测试显示，列表模式的任务成功率与急切加载相当，而成本低于裸桥接层。

如果希望小型工具集采用旧的始终急切加载行为，请设置 `enabled: off`。

## 无法消除的权衡

这些权衡来自提示缓存完整性这一不变量——它们是任何渐进披露设计所固有的，并非此实现特有：

- **冷工具需要一次额外往返。** 模型第一次需要延迟工具时，需要额外花费一到两次模型调用来查找并加载模式。静态侧的 token 节省是真实的，但其中一部分会在运行时付回。
- **延迟模式没有缓存收益。** 已加载的 `tool_describe` 结果会进入对话历史（因此后续轮次确实会被缓存），但它永远无法从系统提示缓存前缀中获益。
- **依赖模型质量。** 工具搜索假定模型能为所需工具写出合理的搜索查询。较小的模型对此做得较差；已发布的 Anthropic 数据（使用工具搜索与不使用工具搜索时，Opus 4 的结果为 49% → 74%）显示了上行空间，也表明约 26 个百分点的准确率仍是检索失败。
- **工具集编辑会使缓存失效。** 在会话中途添加或移除工具会改变桥接工具的描述（其中包含延迟工具数量）和目录，因此提示缓存会失效。这与任何工具集编辑具有相同的权衡。

## 实现细节

- **检索：** 对分词后的工具名称 + 描述 + 参数名称使用 BM25。当 BM25 没有返回正分数命中时，会回退到对工具名称的字面子串匹配，以防止零 IDF 的退化情况（例如，在每个工具名称都包含 "github" 的目录中搜索 `"github"`）。
- **目录跨轮次无状态。** 它在每次组装时都从当前工具定义列表重建——没有按会话键控的 `Map`。这避免了存储的目录与实时工具注册表失去同步这一类错误。
- **目录限定在会话的工具集范围内。** `tool_search`、`tool_describe` 和 `tool_call` 只能看到和调用实际授予该会话的工具。被限制为一部分工具集的子代理、看板工作者或网关会话，无法利用桥接层发现或调用该子集之外的工具——延迟目录是会话自身已启用/禁用工具集的可延迟切片，而不是整个进程注册表。
- **没有 JS 沙箱。** Hermes 使用更简单的“结构化工具”模式（将搜索 / 描述 / 调用作为普通函数）。一些其他实现提供的 JS 沙箱“代码模式”有很大的表面积；我们不采用它。
